# 共同回忆册：八个可行的改进方向

整理日期：2026-10-15。状态：候选方案，供后续开发准备与范围选择，尚未实施或排期。

## 目标与现有基础

让网站成为一本由两个人共同写成、能够反复打开的回忆册。改进重点是内容如何组织、双方如何参与，以及已有记录如何再次被体验。

当前已有日历、按日期保存的日记、私密相册、共同愿望清单和百日信。技术基础为 Astro、TypeScript、普通 CSS、Cloudflare Worker、D1 和 Workers KV；共同密码验证进入资格，当前记录没有双方各自的作者身份。

以下八个方向可以分阶段组合，不要求一次全部开发。沿用暖色纸面、蜡封红、宋体和自然连续阅读；内容只使用双方实际提供或确认的记录。已实现的界面约定仍以 [DESIGN.md](../DESIGN.md) 为准。

## 1. 共同故事页

### 体验

让一次经历拥有完整的一页：日期、文字、多张照片、双方的补充，以及关联的愿望都放在同一篇故事里。日历、相册和愿望分别提供入口，最终翻到同一篇内容。

### 建议首版

- 可以建立、修改和翻看故事，包含标题、日期、正文与关联照片。
- 提供少量适合现有纸面风格的跨页排版，桌面呈现手账组合，手机自然纵向阅读。
- 从日历日期、照片详情和关联愿望打开故事，操作围绕同一篇内容展开。
- 保留旧日记、照片和清单的访问入口，明确关联或迁移策略后再调整数据组织。

### 实现依赖与验收

可沿用现有 Worker、D1 和相册存储，增加故事记录及关联关系。先明确一篇故事与日期、照片、愿望的对应方式，再确定数据库结构。

验收应能完成“建立故事 → 关联现有照片 → 保存 → 换设备重新打开”，并从不同入口看到同一份最新内容；原有私密记录仍可访问。

## 2. 双人视角

### 体验

同一天、同一篇故事里，双方各自留下自己的版本，也能回应对方的段落。可以选择“都写好再一起打开”，让双方完成后再揭晓彼此的回答。

### 建议首版

- 为双方建立各自的身份，故事内明确区分作者与内容归属。
- 双方分别编辑自己的段落，在同一篇故事内阅读与回应。
- 对需要揭晓的内容，明确提交、撤回和开放规则，再提供双人共同揭晓模式。

### 实现依赖与验收

当前共同密码只证明进入者知道密码，不能区分作者。普通署名选择不能提供个人草稿或指定收件人的权限隔离；这些能力需要真实的个人身份与服务端校验。

验收应使用两个独立会话：双方能分别保存自己的段落，更新不会覆盖对方内容；未开放的内容不会通过接口提前返回给另一方。

## 3. 未来邮局

### 体验

把一封固定百日信发展为可以持续使用的来信系统：选择收件人和拆信日期，封好后放进邮局，到日子再打开。也可以双方各封一封，在约定的同一天一起拆。

### 建议首版

- 支持写信、保存草稿、选择收件人和拆信日期、确认封存。
- 邮局展示信封、寄信时间和开放日期，正文按权限和时间从服务端读取。
- 首版以“到日子后，下次访问即可拆信”形成完整流程。
- 后续可考虑关联愿望，在双方确认的完成条件下开放；站外提醒另行选择。

### 实现依赖与验收

依赖双方身份和收件权限，可复用现有百日信的服务端日期门槛。封存后能否修改、如何撤回、双方信件何时共同开放，需要在开发前确定。既有百日信应继续可读。

验收覆盖指定收件人、日期到达前后、封存与撤回规则；未开放正文不进入静态页面、脚本或公开资源。

## 4. 共同桌面

### 体验

提供一张双方能同时进入的纸面桌子：摆放照片、便签和票根，看到对方正在翻哪一页，把照片递到对方面前，一起整理一段回忆。

### 建议首版

- 先做共同翻阅和摆放，集中在一张共享桌面内。
- 同步当前翻看的故事、照片和物件位置，保存双方确认的排列。
- 明确同时操作同一物件的处理方式，断线后能恢复已保存状态。

### 实现依赖与验收

需要实时通信与共享状态。Cloudflare Durable Objects 配合 WebSocket 是可评估的实现路径；它可以协调多个客户端，实际配置、兼容性和成本在实施前复核。

验收使用两台设备同时操作：能及时看到对方的操作结果，断线重连后状态收敛；房间内的记录继续受现有私密访问边界保护。

## 5. 回忆放映室

### 体验

选择一个月份、一篇故事或一组照片，将真实照片、日期和已写下的句子编排为一段短片：照片逐渐铺开、字句出现，最后停在完整手账上。支持手动慢慢翻，也能自动播放。

### 建议首版

- 选择已有故事或照片，并手动调整内容与播放顺序。
- 用少量统一的纸面转场与排版在浏览器内播放。
- 支持暂停、继续、重播和适合减少动态效果偏好的展示方式。
- 文字来自已保存内容；若加入音乐或旁白，使用双方提供且可使用的素材。

### 实现依赖与验收

适合在共同故事页之后开发，可沿用现有照片与日记。首版完成浏览器内观看即可；生成和导出视频文件属于后续独立范围。

验收应能从已选内容生成可完整观看的片段，顺序与文字保持一致，手机可正常播放；退出或会话失效后不残留私密内容。

## 6. 让“往后”走到“后来”

### 体验

让愿望形成完整过程：**想一起做 → 商定时间 → 做完留下记录 → 收进回忆册**。完成时可以贴照片、写两句，把当初的想法与后来的记录放在一起。

### 建议首版

- 在现有愿望上补充双方确认的计划日期，继续支持尚未定日期的想法。
- 完成愿望时可以建立或关联故事，补充照片与文字。
- 从已完成愿望回看故事，也能从故事找到当初的愿望。

### 实现依赖与验收

与共同故事页一起做，复用既有清单入口和保存链路。愿望完成与故事关联的先后关系、取消完成后的保留方式，需要明确，避免误删已写内容。

验收完成一条愿望并建立故事后，刷新或换设备仍能双向打开关联内容；再次调整愿望状态时，故事和照片保持可访问。

## 7. 声音留存

### 体验

在故事或信件里放一张短语音卡，录一段话或上传已有录音，让以后翻到这一天时还能听到当时的声音。

### 建议首版

- 支持录制、试听、重新录制和保存，也可上传适用格式的已有录音。
- 语音卡嵌入故事或信件，播放与查看内容使用同一套权限。
- 开发时确定短录音的时长、大小和格式范围，以及保存失败后的重试方式。

### 实现依赖与验收

网页端可评估 MediaRecorder API，需要实际检查目标手机浏览器的录音格式。增加音频存储与播放鉴权前，应确认账号可用的存储服务和预算；照片上传方案不能直接视为完整的音频方案。

验收在目标设备完成录制、试听、保存和换设备播放；没有麦克风权限时有明确反馈，未授权会话无法读取音频。

## 8. 回忆地图

### 体验

把双方主动记录的地点放到地图上，点一个地方就能翻看相关故事、照片，以及以后想在那里做的事。可以按年份展开，也可以沿一篇故事连接几个地点。

### 建议首版

- 双方手动选择和标记地点，关联已保存的故事或愿望。
- 从地图打开故事，也能从故事定位到关联地点。
- 提供一种清楚的浏览方式，例如按年份筛选，待真实内容丰富后再扩展。

### 实现依赖与验收

适合已有一定地点内容之后开发。地图服务、底图授权、地点查询能力、费用和可用性需另行核实；首版围绕主动标记地点设计，不需要持续定位。

验收能建立地点关联并在地图与故事之间往返，切换年份后只展示对应内容；地点和关联记录遵循相同的私密权限。

## 推荐组合与准备顺序

| 方向 | 主要价值 | 相对当前项目的改造幅度 |
| --- | --- | --- |
| 共同故事页＋愿望变回忆 | 连接现有日历、日记、照片和愿望 | 中到大 |
| 双人视角 | 让双方成为独立内容作者 | 中到大，需要身份与权限 |
| 未来邮局 | 持续使用的期待与仪式 | 中，依赖双方身份 |
| 回忆放映室 | 让已有内容获得新的观看体验 | 中，适合故事页之后做 |
| 共同桌面 | 实时共同在场感 | 大 |
| 声音留存 | 丰富记录的表现力 | 中，需要媒体存储 |
| 回忆地图 | 按地点重新组织回忆 | 中到大，需要地图服务 |

推荐下一轮以 **共同故事页＋双人视角** 为主体，把“愿望完成后留下故事”接进去。准备时先明确故事关联和双方身份，再实现独立编辑与共同阅读；有了完整内容之后，接上回忆放映室。

这一组合的首版完成标准是：两个人能分别给同一篇故事写下自己的版本、关联照片和愿望；从日历、相册和愿望进入，最终翻到同一篇共同完成的内容。

开始具体开发前，应选定首版范围、确认身份方式及既有数据的关联策略，并用合成内容验证独立预览。地图、音频存储和实时服务的账号条件与费用在选用时核实。本文件不固定服务预算或工期。
